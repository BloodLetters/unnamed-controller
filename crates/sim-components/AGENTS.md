# sim-components Development Guidelines & Component Blueprint

## 1. Purpose & Scope

`sim-components` contains concrete electrical and microcontroller board implementations. It models physics, digital logic, peripheral communication, and microcontroller emulation.

**Strict Decoupling**: This crate must remain 100% platform-agnostic and UI-agnostic. It must never depend on `egui`, `eframe`, rendering backends, or windowing APIs.

---

## 2. Component Design Principles

Every component models physical behavior cleanly:
1. **Behavior Independent of Rendering**: A component calculates voltages, currents, state machines, and logic levels. It does not decide colors, pixels, or screen coordinates.
2. **Deterministic State**: Given identical electrical inputs and simulation steps, component state must be fully reproducible.
3. **No Hidden Global State**: Components only interact through declared `PinId` terminals and explicit method calls.
4. **Serialization Ready**: All components must derive `serde::Serialize` and `serde::Deserialize` to support project saving and undo/redo snapshots.

---

## 3. Step-by-Step Guide: How to Create a New Component

Follow this systematic workflow when adding a new component to `sim-components`:

### Step 1: Create Module File (`src/component/<name>.rs`)
Define strong types representing variants and internal physical state:

```rust
use sim_core::component::Component;
use sim_core::netlist::PinId;

/// Color variants for standard LEDs.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, Default, serde::Serialize, serde::Deserialize)]
pub enum ComponentVariant {
    #[default]
    Standard,
    Custom,
}

/// Simulated concrete component model.
#[derive(Debug, Clone, PartialEq, serde::Serialize, serde::Deserialize)]
pub struct ConcreteComponent {
    pin_a: PinId,
    pin_b: PinId,
    variant: ComponentVariant,
    is_active: bool,
    value: f32,
}
```

### Step 2: Implement Constructor & Physical Methods
Provide clean constructors and domain methods:
- Constructor: Accepts base `PinId`s and parameters.
- Electrical update: Accepts node voltages or currents from simulation engine.
- Reversal / Manipulation: Polarity flip or configuration toggles.

```rust
impl ConcreteComponent {
    /// Creates a new component instance with assigned pin IDs.
    pub fn new(pin_a: PinId, pin_b: PinId, variant: ComponentVariant) -> Self {
        Self {
            pin_a,
            pin_b,
            variant,
            is_active: false,
            value: 0.0,
        }
    }

    /// Updates internal electrical state based on applied pin voltages.
    pub fn update_electrical(&mut self, v_a: f32, v_b: f32) {
        let diff = v_a - v_b;
        self.is_active = diff > 1.8;
        self.value = diff.max(0.0);
    }
}
```

### Step 3: Implement `Component` Trait
Implement `sim_core::component::Component` to register pins with the netlist:

```rust
impl Component for ConcreteComponent {
    fn pins(&self) -> Vec<PinId> {
        vec![self.pin_a, self.pin_b]
    }

    fn update(&mut self) {
        // Step time-dependent state machines if applicable
    }
}
```

### Step 4: Export in Module Index
Expose the component in `src/component/mod.rs` and `src/lib.rs`.

### Step 5: Add Unit & Integration Tests
Add comprehensive tests in `src/component/<name>.rs` (module unit tests) and in `tests/component_<name>_test.rs`:
- Verify pin assignment count.
- Verify electrical threshold conduction / state transitions.
- Verify polarity reversal and persistence serialization.

## 4. Microcontroller Board Architecture (`src/board/`)

Development boards (e.g. `Esp32S3DevKit`) implement the `Board` trait and model complete SoC modules:

### 4.1. Core Board Responsibilities
1. **Header Pin Mapping (`HeaderPin`)**:
   - Assigns human-readable names (`GPIO4`, `3V3`, `GND`, `RST`).
   - Categorizes pins by `HeaderSide::Left` and `HeaderSide::Right`.
   - Distinguishes power, ground, and GPIO terminals.
2. **GPIO Controller**:
   - Manages direction (`GpioMode::Input`, `GpioMode::Output`).
   - Manages pull resistors (`GpioPull::None`, `GpioPull::PullUp`, `GpioPull::PullDown`).
   - Reports effective drive levels (`PinDrive::Driven`, `PinDrive::PullUp`, etc.).
3. **Dual Execution Engine**:
   - **Bytecode Engine (`BytecodeVm`)**: Executes high-level virtual bytecode (`OP_SET_HIGH`, `OP_DELAY`, etc.) generated by the built-in sketch compiler. Executes in microseconds without CPU overhead.
   - **Hardware CPU Interpreter (`s3emu`)**: Boots and runs native compiled binaries (ELF/App images with magic `0xE9`).
   - **Cycle Bounding**: Hardware execution in `step()` must strictly clamp CPU cycles (`500..=5000` cycles per tick) to ensure simulation updates complete in under 1ms per frame, preventing UI freeze.
4. **Serial & Peripheral Bus**:
   - Buffers serial transmission (`serial_tx_buffer`) for the host Serial Monitor.
   - Routes I2C / SPI bus transactions to connected peripherals.

---

## 5. Mandatory Engineering Rules

1. **Rule 5 (File Size Limit)**: Keep files strictly under 300 functional lines. Subdivide large boards into `board.rs`, `gpio.rs`, `trait_impl.rs`, and `vm.rs`.
2. **Rule 6 (No Comments in Function Bodies)**: Function bodies must be self-evident. Do not write inline comments between statements.
3. **Rule 7 & 8 (Doc Comments Above Declarations)**: Explain intent, ratings, and invariants directly above struct and function signatures.
4. **Rule 2 (Idiomatic Rust)**: Prefer `Result<T, E>` with domain-specific errors (`FirmwareError`) over panics or unwraps.
